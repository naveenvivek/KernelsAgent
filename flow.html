Use case: a hijacked agent overrides access control

A tenant-data agent may read tenant A's files. Injected instructions make its code try to reach tenant B, steal a key and become root. The same attack ran against four setups. All data and the API key are fake.

Naive is a root container with both tenants mounted read-write and the key in an environment variable. Hardened is non-root, all capabilities dropped, a read-only filesystem and only tenant A mounted read-only. Access control was lost or kept by configuration, whatever the runtime. gVisor added one thing: it hides the host kernel. Fix access control first, then add kernel isolation as the second layer.

  • What the test run found: 16 of 17 cases pass on runc and 15 of 17 on gVisor. Only gVisor hides the host kernel.
  • What gVisor costs: about the same start-up and CPU speed, and roughly 7 times slower on file-heavy work (20,000 file operations: 3.7s against 0.5s).
  • Not yet drawn: Kata would add a third lane with a guest kernel inside a small VM.
